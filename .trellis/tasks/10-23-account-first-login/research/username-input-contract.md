# Registration username input restriction

## User correction and boundary

On 2026-10-25 the user pointed out that registration only rejects invalid usernames on submit, while the input still accepts Chinese and punctuation. The user explicitly restated the set as English letters, digits and underscore. This follow-up supersedes the previous hyphen allowance and the previous UI instruction not to remove input characters. Public registration uses `[A-Za-z0-9_]`, 1–255 characters; optional blank-username ASCII-email fallback remains intact. Existing/imported/provider identifiers and login account entry must remain compatible, including Chinese, email and old hyphenated usernames.

## Input behavior

Restrict the registration username field during editing, including normal typing, replacement, paste and committed IME input. Keep allowed ASCII characters and case, remove unsupported characters, preserve a sensible caret/selection position, and apply the 255-character bound. Filter clipboard text before the native length cap so unsupported prefixes cannot discard legal suffixes; replacement must preserve the field's original trailing text. Do not mutate unfinished IME composition or accidentally submit on its Enter key, including composition-end-before-keydown ordering (`keyCode === 229` after the active flag clears). Preserve ordinary Enter. Include native field constraints/hints where appropriate, without relying on them as the security boundary. Preserve deletion, selection/replacement and optional empty-field behavior. Update all three locales and affected cache references; preserve the icon-font gate and configured password guidance.

Keep a strict raw-value submit guard for programmatic values/autofill that bypass input events, and server enforcement before registration mailbox-proof consumption. Direct API requests containing hyphens or other unsupported explicit username characters return existing HTTP400 `invalid_request` / `validation.username.invalid_format`. Do not sanitize server input into another account name or consume proof on rejection. Preserve raw whitespace/CRLF protection, email/CAPTCHA/registration-switch precedence and intentional blank/null/whitespace-only email fallback.
