# Registration policy feedback and username characters

Supersession (2026-10-25): this document records the completed R16/R17 checkpoint. The user's later R19 instruction narrows explicit registration usernames to ASCII letters/digits/underscore, excludes hyphens and requires active input filtering after committed edits. `username-input-contract.md` governs that follow-up and overrides the former hyphen allowance and no-sanitization UI instruction below. Server raw-value validation and blank-username validated-email fallback remain unchanged in principle.

## User-authorized gaps

The registration/recovery placeholder and legacy translation strings promise six-character passwords, but the actual server policy has a minimum of 12 and an administrator-configurable longer minimum. The existing public `/api/auth/config` already returns the effective `passwordMinLength`; the login page stores but never renders it. The user also requires new registration usernames to exclude Chinese. Root stated the chosen character set: ASCII letters, digits, underscore and hyphen. Existing imported Chinese usernames must continue to log in; display names remain Unicode.

## Boundary and authority

- Retain the current server password policy and administrator settings unchanged. Do not lower the minimum, replace it with a new hard-coded 12, or duplicate the full password validator in the browser. Registration, first-password setup and recovery new-password guidance follows the effective `passwordMinLength` already returned by auth config. Use a neutral localized prompt until a valid config value is available and on failed/malformed config. Reapply dynamic guidance after language changes; ordinary login never acquires a new-password length restriction. Keep actual server policy errors readable.
- Remove stale six-character password promises from shared translations, including old unused profile/error text. For legacy generic error keys lacking a dynamic variable, prefer a truthful neutral message rather than a guessed numeric policy or a visible interpolation token. The profile password modal should show the same public configured minimum; do not change its authentication/update behavior. No unrelated profile redesign or full policy abstraction.
- Validate the raw nonblank explicit registration username using ASCII letters/digits/underscore/hyphen, 1–255 characters (retain existing short usernames; match existing account length boundary). Leading/trailing/internal whitespace is invalid; do not silently trim a nonblank name into validity. Return HTTP 400 with `error:'invalid_request'`, `error_key:'validation.username.invalid_format'` and a readable description. Invalid names cannot create users/sessions/auth codes/tokens or consume a valid registration email proof. Enforce on server, independent of browser.
- Preserve the existing optional-username default to an ASCII email when username is absent/empty/whitespace-only. Existing `isValidEmail` already rejects non-ASCII email; retain its `validation.email.invalid` precedence so fallback cannot bypass the rule, without duplicating or broadening email validation. This exception preserves existing email-as-username clients. Do not add this rule to the generic User model, import, external-provider creation or login/discovery. Do not alter existing stored identifiers. Explicit email-shaped usernames are no longer allowed by the new registration character set; the visible optional-field hint explains both the set and empty-email fallback.
- Add matching visible localized register guidance and frontend validation. Do not silently remove characters or constrain the display-name field. Show invalid-name feedback by the existing active submit/status mechanism. Preserve CAPTCHA, mailbox proofs, OAuth continuation and previous mobile widget/layout corrections.
- Maintain zh/en/zh-TW strings and affected asset cache references. Avoid cache-only changes in unrelated pages; keep the affected auth pair consistent for shared i18n and update profile references if it consumes changed i18n/profile JS.
