# Repository authentication integration research

Read-only source inspection on 2026-11-24. No local checks, tests, builds, application startup, provider calls or Git mutations were performed. This report maps repository contracts; it does not establish the external Aliyun/carrier protocol or live onboarding readiness. Line anchors refer to the inspected source and may move during concurrent implementation.

## Authentication and completed-session boundary

Native endpoints may permit absent browser headers, but still reject cross-origin browser headers. Add only the intended native phone routes; do not disable the global guard. |
| Public login capabilities | `server.js:407`, `/api/auth/config` | Returns sanitized login/registration/CAPTCHA policy. A new phone capability can be exposed here or through a dedicated safe config endpoint; never return server credentials. |

| Account lifecycle lock | `server.js:1672` `finishAccountLogin`, `1682` `withAccountTransaction`; `models/Authenticator.js:8` | Named lock, transaction and fresh user row protect security-state checks through proof consumption and credential issuance. | Final browser issuance | `server.js:1717` `issueLoginWithinTransaction`, `1739` `applyIssuedLogin` | Prefer durable issuance inside the transaction and cookie/alert publication after commit. `isUserBanned` (`server.js:1839`) also rejects `status === 'deleted'`; a bare phone lookup does not enforce this. `services/account-write.js` prevents credential/identity inserts after account erasure. Failed or pending phone authentication must leave an already-active browser account untouched and must not enroll a pending account in the roster.

## MFA and mailbox gates: source dispatch must be extended explicitly

- `pendingLoginSecurityState` (`server.js:1454`) signs the password, email/verification, role/ban, canonical phone/verification and TOTP revision into pending proof. Phone verification changes invalidate an older pending proof. If proving a phone changes account state, create the pending proof from the refreshed account, not the pre-update snapshot.
- `resolvePasswordMailGate` (`server.js:1471`) requires mailbox bind/verify specifically for password login. External OIDC/Huawei currently require TOTP when enabled, otherwise optional configured email MFA for usable non-placeholder mailboxes. Do not label carrier/SMS as `password` merely to reuse code: it changes mailbox requirements and source semantics.
- `createSecondFactorRecord` / `beginOidcSecondFactor` (`server.js:1547`, `1568`) persist pending state in `email_verification_codes`, with a five-minute proof window, challenge hash, saved return path and `sessionDays`. Native clients can echo the pending credential through `X-Oidc-Pending` or `pending_token`; browsers use the HttpOnly pending cookie.
- **Concrete trap:** `getPendingOidcLogin` (`server.js:1580`) treats every non-`password` source as an OIDC/Huawei provider and requires an enabled configured provider. Adding `source: 'sms'` or `'carrier'` without updating this dispatch causes `/oauth2/mfa`, pending projection and completion to reject it. Define an explicit supported source whitelist and source-specific readiness/context validation.
- `/api/v1/auth/oauth/oidc/complete` (`server.js:3408`) distinguishes password, native Huawei OAuth, and external browser issuance. Its pending-purpose check (`3488`), source branch (`3514`), OAuth handoff (`3538`) and return projection (`3572`) all need the same new-source contract. Otherwise a native request can accidentally become a browser-session flow or lose its OAuth parameters.
- Mailbox send/read helpers (`server.js:1777`, `3289`) intentionally accept only password-source mailbox gates. Leave this boundary intact unless the approved requirements explicitly extend the mailbox policy.
- Consume proof/attempt state and issue credentials under the same transaction. A zero-row consume or a later authorization error must roll back completed-success writes; ordinary wrong-code attempts must remain charged. Do not call provider/SMS delivery while holding lifecycle locks.

## Phone ownership, account creation and identity links

- `services/phone.js` owns canonicalization. Use `normalizeParts(countryCode, nationalNumber)` for structured input or provider-separated fields, and `normalizePhone` only for a full number. Use `maskPhone`/`maskE164` for logs or public hints. The generic normalizer is not a provider-specific eligibility validator.
- `models/User.js:54` `create` supports a passwordless account, normalized phone, explicit verified flag/time, and normal role handling. `findByPhone` (`141`) normalizes to E.164 before lookup. `db/init.js:30,38` generates `phone_e164` and enforces a unique index; do not write the generated column directly.
- Existing passwordless accounts use a unique `@users.invalid` placeholder, `emailVerified: false`, and no password (`server.js:2960` Huawei creation). Do not falsely verify a placeholder mailbox or derive public usernames from a clear phone number. Existing `User.create` does not decide registration policy; callers do.
- Conditional phone primitives already exist: `User.bindPhoneIfEmpty` (`324`) and `verifyPhoneIfUnchanged` (`335`). `User.update` also supports guarded administrator verification (`255`) and verifies phone write readback (`268`). A phone proof must bind its exact canonical target, purpose and intended user; a concurrent phone edit must not cause verification of a replacement number.
- `applyHuaweiPhone` (`server.js:2797`) shows safe conflict behavior: bind only if empty, verify only if unchanged, preserve an existing different number, and catch the unique-key race. Never overwrite/merge another account just because a request claims its phone.
- `findOrCreateHuaweiUser` (`2827`) is the stronger creation/linking reference: sorted hashed subject locks on one held connection, transaction, connection-scoped models and release in `finally`. A new phone resolver needs equivalent serialization for the canonical phone so simultaneous first logins cannot create duplicate identities/accounts; the unique index remains the final guard.
- `models/ExternalIdentity.js` stores provider-key-scoped primary/secondary subject IDs and rejects conflicting ownership through `findByProviderSubject`. Use only server-exchanged provider claims. Do not put authorization codes, access tokens or raw SMS proofs in its JSON profile; `buildHuaweiProfile` (`server.js:2756`) stores only identifiers/config snapshots and masked phone metadata.
- Existing Huawei automatic phone matching requires both an upstream-verified phone and an already-verified local phone (`server.js:2926`). Whether a new SMS proof may claim an existing unverified local phone is a product/security decision, not an existing granted behavior. Do not silently inherit a different rule by reusing `findByPhone` alone.
- Preserve global `registration_enabled` and the client-specific QFLI registration contract (`.trellis/spec/backend/registration-policy.md`; `services/qfli-integration.js`). Current QFLI policy permits Huawei creation and blocks other external signup. If carrier signup is now intended for QFLI, record that explicit scope change and update every new-account path consistently; existing-account login is a separate concern.

## Durable proof, replay and abuse controls

- `models/EmailVerificationCode.js` provides durable `create`, exact-ID lookup, latest active lookup, conditional attempts, one-time `consume`, invalidation and persisted JSON context. `db/init.js:235` uses `purpose VARCHAR(32)`, `email VARCHAR(255)`, optional user FK, attempts and expiry; there is no SMS model/table today.
- This is a useful implementation pattern, not a reason to represent phone numbers as emails accidentally. Freeze whether phone challenges get a dedicated model/table or an explicitly namespaced durable representation; separate SMS login, phone verification and carrier replay purposes. Bind a verification challenge to the authenticated user and exact phone; native login challenges must retain their OAuth/application context and chosen duration.
- `models/RateLimit.js` hashes keys, atomically increments durable windows and returns `retryAfter`. Reuse distinct per-phone, per-IP and per-purpose keys for send and verify; charge failed attempts and resend cooldowns rather than relying on process memory. `server.js:2268` illustrates cooldown, invalidation, hashed proof and invalidating a code after delivery failure.
- `verifyEmailCodeWith` (`server.js:2344`) is the connection-scoped consume pattern; the generic verifier uses global models and must not be invoked from a held transaction. Provider authorization/token proof replay protection also needs durable state; the old in-memory Huawei binding cache is not a restart-safe model to copy.
- `services/account-erasure.js:51-54` deletes identity/session and email-proof rows; any new account-bound phone-proof table must join erasure cleanup. `server.js:6380-6399` initializes models and performs expiry cleanup; wire a new model there if needed.
- Current schema is **8** (`db/init.js:277`). Startup checks the version and does not migrate (`350-364`). A new table requires explicit migration/schema/release integration; the task's no-local-execution constraint means migrations are not run locally.

## Configuration, admin UI and operator entry

- Non-secret policy values use SQL `settings` through `getSettingValue`/`saveSettingValues` (`server.js:334,351`), defaults (`318`), and admin security GET/PUT (`6008,6218`). All mutations call `requireAdminUser` and the global same-origin guard, then a redacted `recordAdminLog`.
- Secret-bearing runtime overrides use `services/admin-settings.js:createStore`: private path outside `public/`, AES-GCM through `services/secret-storage.js`, temporary file + fsync + rename, and strict decrypt-on-load. **Both `load()` and `save()` whitelist only SMTP/Turnstile today.** A new carrier section added only to an in-memory object will disappear at save/restart. Preserve unrelated sections and implement validation/encryption/redacted projection together.
- `server.js:5928-5958` Turnstile configuration is the clean blank-secret-preserves-current / explicit-clear example. Expose `configured`/`hasSecret` and readiness reasons, never the original key. `bootstrap` (`6373`) loads persisted overrides before model initialization. New configuration must be loadable while disabled and incomplete; enabled runtime calls must fail closed until onboarding credentials are complete.
- Existing provider storage is `models/OidcProvider.js` / SQL `oidc_providers`, encrypted secrets at the server boundary, and `/api/admin/oidc` GET/POST/DELETE (`6119-6195`). The accepted types are currently only `oidc` and `huawei_quicklogin` (`server.js:653-656`); `views/admin/security.html:141` repeats that list. Unknown types currently fall back during config conversion, so adding a carrier type requires coordinated validation, hydration, enabled/readiness logic and UI—not just another option label.
- Standard operator OAuth can use the existing OIDC/OAuth2 entry only if its real token/UserInfo contract matches the supported protocol. `server.js:2510` login state contains server-configured provider, nonce, PKCE, safe return path and session duration; callback validates these before identity resolution. Specialized carrier signatures/exchange belong in a dedicated `services/` adapter; no arbitrary request-selected upstream URL/credentials or fake successful phone response.
- `public/js/pages/auth/login.js:265` renders configured provider login links and preserves the duration and OAuth return path. Its `submitAuthForm` (`791`) recognizes `mfa_url` only for the existing login form; a new SMS/H5 form needs explicit continuation handling, visible errors, busy guards and preservation of the account chooser add/back flow. Do not expose carrier secrets to browser SDK initialization.
- UI/config owners: `views/admin/security.html`, `public/js/pages/admin/security.js`, `views/auth/login.html`, `public/js/pages/auth/login.js`, `public/js/shared/i18n.js`; version changed asset URLs consistently. Profile phone-verification UX, if in scope, is `views/account/profile.html` and `public/js/pages/account/profile.js`, distinct from the administrator's manual verification checkbox.

## Recommended implementation ownership and CI handoff

Keep one owner of `server.js` for guards, route registration, continuation dispatch and final issuance. Other workers can independently own provider adapter/config persistence, UI, and durable challenge/schema/tests after the API/context shape is frozen. Avoid split ownership of the pending source branches.

CI-only validation already starts at `.github/workflows/build-and-release.yml` -> `scripts/ci-backend.sh`; image publishing depends on the test job. New provider/phone cases should be executable by that workflow without real credentials: disabled/incomplete configuration, provider business errors and replay, verified-phone ownership conflicts, pending MFA preserving A, final B login retaining A, exact session duration, native no-cookie OAuth handoff, phone-scope redaction, SMS cooldown/attempt/replay, concurrent binding and erasure. Any added browser validation must be deliberately wired into CI; local screenshots or local command execution are not part of this task's authorized validation.
