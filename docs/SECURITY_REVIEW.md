# 登录网关安全审查记录

日期：2026-09-15。

原代码不能直接作为生产登录网关上线：初始化脚本写入公开固定凭据的管理员和客户端，首次注册存在隐式提权，会话撤销、授权码消费和外部身份绑定也存在安全缺陷。本次已在工作区修复下列问题，并完成隔离回归及浏览器验证。

## 已修复的问题

| 风险 | 原行为 | 修复后的行为与位置 |
| --- | --- | --- |
| 高危：初始化写入固定身份 | `init-db` 创建演示管理员和多个固定密钥客户端；应用含内存演示分支 | 删除 `config/demo-clients.js`。`scripts/init-db.js` 只执行结构迁移。内存适配器移到 `tests/support/`，正式启动仅支持 MySQL |
| 高危：隐式管理员提权 | 没有管理员时自动提升首个用户，或按环境邮箱在启动时提权 | 删除启动提权和首用户提权；`models/User.js` 默认角色固定为普通用户 |
| 高危：弱密钥和签名边界 | 默认 JWT 密钥、空 JWKS，客户端缺少独立公钥验证方式 | `config/runtime.js` 拒绝弱/占位密钥；`services/signing.js` 使用持久化 RSA 私钥签发 RS256 Access / ID Token，发布实际 JWKS；会话和刷新凭据校验用途、签发者和对应数据库记录 |
| 高危：会话撤销失效 | 将 JWT 中的会话 token 当作数据库主键撤销；排除当前设备时同样混用 ID | 所有撤销使用实际会话行 ID；续期更新同一行并设置绝对存活上限；检查会话所属用户；测试旧 Cookie 重放及保留当前设备 |
| 高危：授权码/刷新凭据重复使用 | 授权码读取与删除之间存在并发窗口；刷新凭据可反复使用 | 授权码及刷新凭据使用数据库条件删除和 `affectedRows` 确认单次消费。刷新返回替代凭据；严格校验客户端、回调地址和 S256 PKCE |
| 高危：外部身份接管和 MFA 绕过 | 外部邮箱匹配即自动绑定本地账号；外部登录直接建立会话 | 不按邮箱自动合并。绑定要求最近登录并保持发起绑定的同一会话；外部登录执行本地 TOTP/邮件 MFA。严格验证 nonce、issuer、audience、到期时间、subject 与 UserInfo 一致性 |
| 高危：覆盖已绑定验证器 | setup 可替换已经启用的 TOTP secret，恢复码与动态码存在重放窗口 | 拒绝覆盖已启用验证器；新绑定要求最近登录。TOTP counter、恢复码和邮件验证码均进行原子消费；新 TOTP secret 加密保存，恢复码长度提升并可通过页面输入 |
| 高危：凭据撤销不完整 | 改密仅撤销 Cookie 会话，OAuth 凭据仍可使用；客户端停用缺少完整撤销 | 改密、重置、封禁、管理员强制退出和客户端修改撤销对应网关凭据；UserInfo / Introspection 检查当前用户和客户端状态 |
| 高危：伪造来源与请求 | 限流直接采信 `X-Forwarded-For`；CORS 响应头不能阻止跨站写入 | 仅信任明确配置的代理 IP/CIDR。账号限流和请求限流使用 MySQL 共享状态；浏览器写操作验证同源 Origin / Referer / Fetch Metadata |
| 验证码失去实际作用 | SVG 直接包含验证码明文字符，邮件不可用时把验证码写到日志 | CAPTCHA 改为 PNG，答案散列保存在数据库并单次消费；SMTP 不可用时失败，不输出验证码。公开发码入口限于注册和密码重置 |
| 敏感信息与 scope 越界 | ID Token / UserInfo 总返回用户资料；令牌和客户端密钥明文存储 | 用户声明按 `openid` / `profile` / `email` 区分。新客户端密钥使用加盐 scrypt，Access / Refresh Token 保存摘要；新验证器数据加密存储 |
| 不当自动数据库配置 | 空提供方表会从环境配置重新导入；删除后可能重新启用 | 提供方只来自数据库，启动不导入、不补齐业务配置。无法解密的提供方停止提供登录，管理员可重录密钥 |
| 生产页面含不安全入口 | `/callback` 反射未转义输入；遗留成功/consent 页面信任任意跳转；依赖运行时 CDN 脚本 | 删除测试回调和失效页面逻辑，旧成功/consent URL 转向实际流程。脚本、样式和字体均本地分发，CSP 不允许内联脚本或远程脚本 |
| 配置写入不一致 | 无效安全设置请求可能先修改部分开关；修改禁用客户端可能恢复启用 | 安全设置完整验证后通过单条 SQL 原子写入；省略 `isActive` 保留原状态 |
| 已公布的依赖漏洞 | 初次审计发现 2 个高危、3 个中危依赖项 | 更新 Express、mysql2、Nodemailer 及相关依赖和锁文件。最终生产依赖审计为 0 |

普通应用凭据授权不再依赖伪造的系统用户：`client_credentials` 以客户端为主体，令牌表中 `user_id` 为空，不允许申请用户身份 scope。

## 手机号与华为一键登录（结构版本 2）

本次为登录网关补充手机号支持与华为账号一键登录，结构版本从 1 升到 2。以下是这部分引入的安全边界。

| 关注点 | 处理方式 |
| --- | --- |
| 手机号作为身份标识被污染 | 所有写入路径统一经 `services/phone.js` 归一化为 E.164；唯一性由存储生成列 `phone_e164` 上的唯一索引 `uq_users_phone_e164` 在数据库层保证，不依赖应用层判断 |
| 国家代码与国家号码拼接产生错误合并 | 明确区分国际国家代码（存储）与国内长途冠码（仅用于解析、从不存储）。`+1` / `+7` 无冠码的例外单独处理，避免 `+1 8005550100` 与 `+18 0055 50100` 数字串相同而被误判为同一号码 |
| 手机号自助修改绕过验证 | 本次未接入短信通道，因此**不提供**自助改号入口，个人资料页只读展示掩码。手机号只能来自华为一键登录（已验证）或管理员配置 |
| 运营商二次放号导致账号接管 | 华为一键登录的手机号自动绑定开关 `huawei_phone_autolink` **默认关闭**。打开后若手机号已属于其他账号，保留原绑定、不静默合并，并在登录日志记为 `phone:conflict` 供运维核查 |
| `open_id` / `union_id` 大小写被折叠导致串号 | 两个标识都以区分大小写的 `utf8mb4_bin` 存储并建唯一索引；匹配先按 `open_id`、再回退 `union_id`，命中后补齐缺失字段 |
| 上游凭据或报文泄露到日志 | 华为适配层把失败统一折叠为 `invalid_grant`，不回显上游响应体、不记录 `client_secret` 或 token |
| 机器调用接口被跨站利用 | `quick-login` 与 `oidc/complete` 按“机器调用”判定：仅在 `Sec-Fetch-*` / `Origin` / `Referer` 证明是跨站浏览器请求时拒绝，服务端调用放行；按来源 IP 限流（30 次 / 10 分钟） |
| 原生 App 被迫使用 Cookie 而弱化二次验证 | 二次验证凭据通过 `X-Oidc-Pending` 请求头或 `body.pending_token` 传递，App 无需 Cookie jar；响应中的 `pending_header` 字段让 App 不必硬编码头名 |
| 合成邮箱成为不可达的验证码目标 | 华为未返回邮箱时写入 `@users.invalid` 占位邮箱，二次验证**不会**走邮件通道，改用验证器，避免向不存在的地址发码 |
| 外部提供方调用协议混淆 | 通用 OIDC 使用 `userinfo_method` / `userinfo_token_in`。华为一键登录授权码接口单独使用 `account-api.cloud.huawei.com` 上的 POST + JSON `code/clientId/clientSecret`，解析 HTTP 200 的 `resultCode`，并区分凭据、权限、授权码与上游错误；不把旧版 Access Token + form UserInfo 协议用于授权码接口 |
| 手机号声明越权返回 | 新增 `phone` scope。`phone_number` / `phone_number_verified` 仅在客户端显式申请该 scope 时出现在 UserInfo 和 ID Token 中 |

**迁移风险**：`phone_e164` 是存储生成列，迁移时不要手工写入。若现有数据中已存在重复手机号，`init-db` 会因 `uq_users_phone_e164` 唯一索引冲突失败，需要先人工清理重复数据再迁移。`oidc_providers` 新增字段均有默认值，已有提供方不受影响。

**本次未做的部分**：未接入任何短信通道，因此手机号目前不能通过短信验证码自助绑定或改号；未实现按手机号自动合并本地账号。

## 当前上线阻碍与迁移边界

本地 `.env` 检查结果：`NODE_ENV=development`、`JWT_SECRET` 未通过生产强度检查、未配置 `OIDC_SIGNING_KEY_FILE`。本次没有修改其中的凭据。应依据 [.env.example](.env.example) 和 [README.md](README.md) 完成正式配置。

启动错误排查补充：本地 JWT 密钥长度为 33 字节，但仍命中示例占位值检查。已将错误细分为缺失、占位、过短和重复度过高，并固定从项目根目录加载 `.env` 和相对密钥路径。新增 `npm run check:config` 只读预检，显示有效配置来源及长度，不打印密钥；进程管理器注入的环境变量仍保持优先级。未自动生成或替换既有部署密钥。

上线前必须在目标环境完成数据库备份与显式迁移、HTTPS 代理、SMTP、实际第三方提供方和业务客户端的联合验证。本次未连接或修改真实数据库，未发送真实邮件，未重启或部署既有服务。

迁移新增限流、验证码和结构版本表，补齐 nonce / TOTP counter 字段，扩展加密字段、允许应用令牌没有用户，并将外部 subject 列设为区分大小写。结构版本 2 追加手机号字段与生成列、`user_identities.provider_secondary_id` 以及 `oidc_providers` 的 provider 类型与 userinfo 调用方式字段。`npm start` 不执行这些 DDL，须由运维执行 `npm run init-db`。迁移不创建管理员、客户端或外部提供方，也不自动更改用户角色。

源代码清理不会删除历史数据库记录。旧脚本涉及的标识包括：

- `demo@vaultsso.com`、`system@vaultsso.local`
- `salesforce-prod`、`slack-workspace`、`github-enterprise`、`azure-portal`、`azurekiln-main-site`

这些标识是否实际存在、是否已被业务复用，需要由数据库负责人核实。尤其应处理演示管理员和历史公开的固定密钥；本次没有按名称自动删除业务数据。生产客户端认证已经拒绝不足 32 字节的旧密钥。

生产签名与会话规则发生变化，现有登录需要重新建立；调用方须支持 S256、RS256、公钥校验和刷新令牌轮换。更换 `JWT_SECRET` 还会影响既有加密凭据，应安排重录和验证器恢复。RSA 签名密钥可通过保留旧公钥进行独立轮换。

JWT 的离线签名验证只能确认签名与时效。业务 API 若要求立即感知停用或撤销，需要调用网关 Introspection；仅离线验签的调用方可能持续接受令牌直至其过期。

当前协议范围是管理员注册的可信机密客户端；未实现公开客户端、逐次用户授权确认、`prompt`、`max_age` 或非 query 响应模式。未支持的相关请求被明确拒绝。本次通过的测试不是完整 OIDC 一致性认证或线上渗透测试结论。

工作区原有 `azurekiln-oauth2.zip` 未重新生成；它不是本次修复的发布产物。修改尚未提交或推送。
