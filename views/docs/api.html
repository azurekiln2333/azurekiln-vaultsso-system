Authorization Request

GET /oauth2/authorize?response_type=code&client_id=YOUR_CLIENT_ID&redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback&scope=openid%20profile%20email&state=RANDOM_STATE&nonce=RANDOM_NONCE&code_challenge=BASE64URL_SHA256_OF_CODE_VERIFIER&code_challenge_method=S256

Clients require PKCE by default. Administrators may disable it for a client that cannot support PKCE, but this reduces protection against authorization-code interception. For clients with PKCE disabled, both code_challenge and code_challenge_method may be omitted; if either is sent, both must form a valid S256 pair. The challenge is computed per request, never copied: it is the SHA-256 digest of code_verifier encoded as unpadded base64url, so it is exactly 43 characters of [A-Za-z0-9_-]. Token redemption requires the matching verifier whenever the issued code contains a challenge, regardless of later client-setting changes.

Registration And New Passwords

Read GET /api/auth/config for the effective passwordMinLength before presenting registration, first-password, recovery or password-change guidance. The default minimum is 12 characters; administrators may configure a longer minimum up to 64. Use neutral guidance while configuration is unavailable. The server still validates the complete password policy and returns its actual requirement in error_description with validation.password.weak; the minimum is guidance, not the entire acceptance rule.

For POST /oauth2/register, a nonblank explicit username must contain 1–255 ASCII letters, digits or underscores ([A-Za-z0-9_]); hyphens and spaces are rejected. The web registration field filters unsupported characters during editing, while the API validates the original supplied value without sanitizing it. Omitted, null, empty or whitespace-only usernames retain the existing default to the validated email address; an explicitly supplied email-shaped username is rejected. Invalid names return 400, error: "invalid_request" and error_key: "validation.username.invalid_format" before consuming the registration email proof. Existing registration-switch, CAPTCHA and email-validation errors retain precedence. Unicode display names and existing/imported Unicode or hyphenated account login remain supported.

Account-First Sign-In

An account created without a local password can start from the account instead of the password. Send POST /oauth2/authorize as JSON with discover_account: true and username, plus the original OAuth parameters when the flow must be validated. The username field accepts the account name or its email. Discovery is stateless: it never sets a cookie, issues a session, token or authorization code, and never sends mail.

POST /oauth2/authorize
Content-Type: application/json

{ "discover_account": true, "username": "alice", "client_id": "YOUR_CLIENT_ID", "redirect_uri": "https://app.example.com/callback", "code_challenge": "BASE64URL_SHA256_OF_CODE_VERIFIER", "code_challenge_method": "S256" }

Successful discovery answers 200 and reports the next step in next: password when the account has a local password or the identifier matches multiple existing accounts, set_password when the account has no password and has a usable mailbox, and contact_admin when no usable mailbox exists. An identifier with no matching username or email returns 404 with error: "account_not_found", error_key: "auth.account_not_found" and error_description: "账号不存在", without a next step or account metadata. Existing account-ban, lock, OAuth-validation and HTTP-throttling errors still apply; lock and OAuth errors take precedence over missing-account feedback. Ambiguous matches never select an account. Only set_password includes email_masked, a partial destination such as al***@example.com; the full address is never returned.

{ "next": "password" }
{ "next": "set_password", "email_masked": "al***@example.com" }
{ "next": "contact_admin" }

First-Password Setup

When discovery answers set_password, request the code with the account identifier instead of the address. POST /api/email-verification/send accepts { "username": "alice", "purpose": "password_reset" }; the server re-derives the stored address, so the caller cannot choose the destination. Sending username and email together is rejected with 400 auth.password.setup.invalid_identifier. An account that already has a password returns 409 auth.password.setup_changed, and an account with no usable mailbox returns 400 auth.password.contact_admin. Unknown and ambiguous identifiers keep the generic 200 acknowledgement and no mail is sent.

Then submit POST /api/password-reset with { "username": "alice", "email_code": "123456", "password": "NEW_PASSWORD", "confirm_password": "NEW_PASSWORD" }. The code is verified against the same password_reset purpose and the resolved account, and the password is written only while the account still has none, so a concurrent change returns 409 auth.password.setup_changed before any session or token is revoked. Success answers 200 with message_key: "auth.password_reset.updated"; the user is not signed in and continues with the normal password step.

Both /api/email-verification/send and /api/password-reset remain backward compatible. A request that supplies only email keeps its original semantics, including sending to that address and resetting the password of the account that owns it. The username variants are additional and are selected by field presence, so supplying both identifiers is always rejected.

Token Exchange

POST /oauth2/token
Authorization: Basic base64(client_id:client_secret)
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=AUTHORIZATION_CODE&redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback&code_verifier=CODE_VERIFIER

Send code_verifier when redeeming a code issued with PKCE; codes issued without a challenge do not require one. The initial token response includes refresh_token only for offline_access. Every refresh rotates that credential: replace the stored refresh token with the new response value. ID Tokens require openid; profile and email claims require their corresponding scopes.

The non-standard roles scope adds role and isAdmin to the UserInfo response and the ID Token. It is intended for first-party clients that gate their own admin surfaces, and must be registered on the client before it can be requested.

The phone scope adds phone_number (E.164, e.g. +8613800138000) and phone_number_verified. Without it those claims are omitted entirely. Phone numbers are normalized server-side; the national trunk prefix (0 in 013800138000) is stripped, while the country code (86) is stored and drives uniqueness.

Merge An External OIDC Account

Sign in again to the account to keep, then use the provider's Merge account action on the profile page. It starts GET /api/v1/auth/oauth/oidc/login?provider=PROVIDER_KEY&intent=merge&return_to=/profile. The gateway stores the target session in signed state and requires the same session to be less than five minutes old at start, callback and transaction. The provider authorization-code exchange proves the source identity. Success returns to /profile?account_merged=1; failure returns to the profile with an error message.

Only an automatically created ordinary source account with one provider identity and no local password, authenticator, phone, credits or modified profile can be merged. A verified provider email may be retained in the moved identity, but never replaces the target email. The transaction moves the identity and app-use history, deletes the source and its credentials, revokes other target sessions/tokens and keeps the current target session. Conflicting or populated source accounts require manual review. Matching email alone never authorizes a merge.

Huawei Account Kit Quick Login

For applications with the Huawei Account Kit quick-login permission: the HarmonyOS client sends its short-lived Authorization Code over HTTPS to its application server. The application server calls this gateway's quick-login API. The gateway exchanges the code, resolves the Huawei identity and returns a login result or a pending binding/MFA step. Only the gateway calls Huawei with POST JSON { code, clientId, clientSecret } at https://account-api.cloud.huawei.com/oauth2/v6/quickLogin/getPhoneNumber. The client never receives the Huawei secret. An upstream HTTP 200 can still carry a failing resultCode.

Only a complete, usable Huawei phone returned for this login is exposed as E.164 phone. phoneStatus is verified, conflict, unverified, not_returned, or scope_not_granted for an OAuth handoff without approved phone scope. phoneBinding reports whether the local phone binding succeeded. Pending binding and MFA responses are not final user data. Missing permission or an unusable Huawei response cannot produce a complete phone.

Bind Or Skip

Keep binding_token on the application server for at most five minutes. To bind, first complete the existing account's password, CAPTCHA and second-factor login through /oauth2/authorize and /oauth2/token, then call POST /api/v1/auth/oauth/huawei/bind with { "binding_token": "..." } and that account's bearer access token. The access token must belong to the same OAuth client. A successful bind consumes the pending token; use the existing account's tokens to finish login. To create a new account, call POST /api/v1/auth/oauth/huawei/skip with the pending token and the original OAuth authorization parameters. Skip also consumes the token and returns the normal authorization-code or MFA response. Expired and replayed tokens are rejected.

Identity verification is phone-based for the QFLIStudio+ client only. When the client_id of this Huawei request starts with qfli (case-insensitive), quick login, /huawei/bind, /huawei/skip and intent: "link" all return 403 huawei_verified_phone_required ("请使用已绑定手机号的华为账号") whenever this exchange produced no complete phone with phoneNumberValid true. No account, identity binding, pending token or session is created, and no existing account is modified. Pre-existing Huawei bindings recorded without a phone can no longer sign in for a QFLI client. Every other client, and any request without a client_id, keeps the previous behaviour: binding_required is still issued, /skip still creates the account, /bind still attaches the identity and a stored phone-less account still signs in, simply without a phone. Only intent: "merge" is exempt for every client, because it moves an already existing source identity into the signed-in target account.

Merge An Accidentally Created Account

Sign in again to the existing target account, then within five minutes call the same quick-login endpoint using that account's gateway session cookie and a newly obtained Huawei code: { "intent": "merge", "provider": "huawei-main", "authorizationCode": "FRESH_CODE" }. The code proves the separate source identity. On success, the gateway atomically transfers safe Huawei bindings and app-use history, revokes source credentials and deletes the disposable source account. It preserves the target account's password, role, email and authenticators. A source with its own password, authenticator, meaningful profile data, credits or a phone conflict is rejected with 409 for manual review. A stale target session receives 403 reauthentication_required. Matching a UnionID within one trusted huaweiUnionScope already resolves unconflicted App OpenIDs to one local account; it does not need a merge call.

Second Factor Without Cookies

POST /api/v1/auth/oauth/oidc/complete
X-Oidc-Pending: PENDING_TOKEN
Content-Type: application/json

{ "code": "123456" }

The pending token may also be sent as body.pending_token. Use the pending_header value from the previous response. After Huawei MFA with OAuth handoff, completion returns { authorization_code, state, redirect_uri, redirect, user, phone, phoneStatus, phoneBinding } without a gateway session cookie; redeem the authorization code next. Without OAuth handoff it returns { redirect, user, phone, phoneStatus, phoneBinding } and a gateway session cookie. The full phone in OAuth responses still requires requested and granted phone scope.

Without that scope or a returned UnionID, matching stays app-local. Phone Autolink

The huaweiPhoneAutolink security toggle controls matching an unbound Huawei identity to an existing account with the same verified E.164 phone. Its current new-deployment default is on; read the actual setting from the config endpoint because an administrator may change it. Carrier number reassignment can let a new owner claim an older account, so review this policy for each deployment. A missing, invalid or masked Huawei number cannot be used for matching. A phone conflict never overwrites the account's stored number.

If Huawei does not return an email, the gateway stores a synthetic @users.invalid placeholder and deliberately skips the email second-factor channel, so codes are never sent to an unreachable address. Such accounts fall back to an authenticator app.

This endpoint is treated as a machine caller: it is rejected when Sec-Fetch-*, Origin, or Referer prove a cross-site browser request. It is rate limited to 30 requests per 10 minutes per source IP. Huawei errors use fixed responses: invalid/expired code 400, missing permission 403, provider credential or client mismatch 503, and upstream/network failure 502. Raw upstream bodies, codes, phone numbers and credentials are not echoed to callers.

Admin APIs

These endpoints and the admin pages require a signed-in administrator. Browser account and admin write requests must be same-origin. Client secrets are provided only when created or explicitly changed, and stored as salted hashes.
